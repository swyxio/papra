# SwyxDrive private feedback

A recipient can open **Report a download problem** after trying a shared download. The same form opens from preview and upload errors, web Help, and the standalone Smolhuman desktop Help menu. A receipt link contains a random 256-bit key in its fragment. Anyone who holds the link can read and reply to that report. Support cannot reconstruct a lost key.

Each receipt shows the report, private conversation and engineering timeline. A verified release adds a durable notice to each linked receipt. Open receipts refresh every 30 seconds. Email is optional contact information for a reviewer. The service delivers automatic notifications on receipts. Attachments are UTF-8 text up to 12 KB, shown after redaction and visible only to the reporter and the Drive owner.

## Intake and investigation

The form saves an encrypted draft in the browser before submitting. A private retry link works in that browser and retries automatically when it comes back online while the page is open. It retains the same submission ID and receipt key if the initial acknowledgement was lost. A successful server response supplies the feedback ID. If browser storage is unavailable, keep the form open to retry.

D1 commits the private report, bug link, timeline entry and eligible dispatch intent in one batch. The existing five-minute Worker cron drains the outbox. A receipt identifies its own conversation. The engineering bug and its numbered investigation generations can be shared by many receipts. Each generation tracks its provider session, PR, reviewed head and released version separately.

The Worker signs observed response metadata. A tracked native-download URL carries an operation ticket scoped to its version path. The file route independently checks the share grant on every request. Failed transfer metadata expires after seven days. A successful handoff does not prove the browser saved the file. Upload retries and media checkpoints appear only when the client observed them. Diagnostics exclude request URLs, headers, filenames and document contents. The form redacts recognized credentials, URLs and private paths in free text and lets the reporter inspect the result.

Only two independently identifiable product failures currently dispatch automatically. A valid single range was rejected relative to the size in the server's own response, or encoding the attachment display label failed. The agent receives the engineering ID and generation, defect signature, operation, stage, HTTP status, deployed source SHA, and a fixed local synthetic media recipe. Private messages, contact details, attachments, operation IDs and raw errors never go to Devin. Security concerns, attachments, uncategorized errors and all other product areas enter human triage.

## Reviewer queue

Open **Help → Feedback review** as the Drive owner. Request information on one receipt, reply, group a report into another bug with the same operation, or record a decision. Grouping changes the engineering link while keeping each private conversation separate. A fresh matching failure observed after a verified release reopens the bug. Retrying an old submission preserves its original receipt.

The queue can link an open draft in the correct product repository. Its PR description must contain nonempty **Before**, **After**, **Tests** and **Remaining uncertainty** sections. Inspect the evidence and code, then record review for that head. Merge using the ordinary human GitHub workflow. A changed head requires a new review.

The dispatcher holds a lost or timed-out create acknowledgement for manual reconciliation. Search the configured Devin organization for the exact tag `feedback-<bugId>-g<generation>`, then link the matching session. An explicit rate-limit response can retry. A definitively rejected dispatch can be retried from the queue after its configuration is fixed. A crash between reserving a run and receiving confirmation also enters reconciliation. Another generation cannot start while a previous provider run may still be active.

Web verification checks the merged, reviewed PR and the SHA actually served by `https://drive.swyx.io/api/health`. Desktop verification requires a published GitHub release, a nonempty uploaded Smolhuman Mac installer, and a tag containing the reviewed merge. A tag, CI build, or local playtest install alone cannot release a receipt. The verifier supports a specific desktop tag in the queue or the latest published release on cron.

## Release setup

1. Before deploying the web Worker, apply the additive migration to the existing Drive database. From `apps/papra-worker`, use `pnpm exec wrangler d1 execute papra-drive --remote --file migrations/0007_feedback.sql`. Fresh local databases can use `schema.sql`. The migration is idempotent.
2. Deploy the reviewed web change through the existing release coordinator. The standard build embeds its Git SHA in the client. Verify the live health SHA, signed-out form and private receipt on a small synthetic shared file before shipping the desktop menu. Intake and human review work with Devin disabled.
3. For automatic dispatch, provision an organization-scoped Devin service user that can read its configuration and create/read its own sessions. Attaching an explicit profile requires the security-profile management permission. Scope the GitHub installation to `swyxio/papra`. Require at least one approving review on main and exclude the provider identity from bypass and administration. Give it only the access needed to push topic branches and open draft PRs. Keep deployments and production credentials outside its environment. The Worker checks for a required PR review using active rulesets or classic branch protection. [Devin session API](https://docs.devin.ai/api-reference/v3/sessions/post-organizations-sessions) · [GitHub branch rules](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch)
4. Use a disposable, preinstalled checkout with synthetic fixtures. Configure a mandatory organization security profile with repo read/write, read-only Devin MCP, no other MCP servers, and egress restricted to the GitHub hosts in `feedback-providers.ts`. The preflight checks that the service user sees just the intended repository and profile before each billable start. Set `DEVIN_API_KEY` (service key beginning `cog_`), `DEVIN_ORG_ID`, and `DEVIN_SECURITY_PROFILE_ID` as Worker secrets using `pnpm exec wrangler secret put NAME`. Never copy a personal CLI login into the Worker. The limits are three ACUs per session and two starts in a rolling 24 hours, including ambiguous starts.
5. Set `FEEDBACK_GITHUB_TOKEN` if authenticated GitHub reads are needed for private release evidence, classic protection or rate limits. Use read-only contents and pull-request access for the two product repositories, and administration read only if needed to inspect classic protection. This token stays in the Worker. The coding session receives no Worker secrets.

Check intake and releases locally with `pnpm --filter @papra/worker test`. The suite uses Miniflare D1/R2, a generated 1 KiB WAV and fake Devin, GitHub and deployment responses. To check web error actions, private receipts and retry behavior in Chromium, run `pnpm --filter @papra/app-client build` and `node apps/papra-client/scripts/feedback.browser.mjs` with Playwright Chromium installed.

Run the native-download regression against the built client and real local Worker with `pnpm --filter @papra/worker exec vitest run --config scripts/vitest.feedback.config.ts`. This serves the application on loopback, injects a download-label error, submits from Chromium, and checks the reporter's verified-release notice. All external provider and release reads are fake.
